# Grok Bot: Concrete Specifics

**Core abstractions**

- **Bots:** Always-on "AI teammates" you message from desktop or iPhone. They can message each other, share context in threads, and coordinate in group chats.
- **Computer:** Each account gets one persistent cloud computer with a browser, filesystem, and terminal. Every Bot gets its own screen on it. The docs say all Bots share this machine.
- **Skills:** A skill "describes how to perform a task."
- **Routines:** A routine "assigns a workflow to one Bot and tells it when to run," on a schedule or, where supported, after an event.
- **Approvals:** Desktop offers "Allow once," "Deny," and "Always allow." iPhone offers "Approve once" and "Deny." A model-based Auto Review layer can apply rules, and "Require Approval" rules override "Always Allow" rules.
- **Local computer access:** A separate setting (Settings → General → Agent → Execution on Local Computer) defaults to "Ask every time."
- **Connectors and memory:** The page does not describe either.

**How tasks are assigned**

- You message a Bot like a colleague and hand it a job. It works across apps and inboxes, finishes end to end, and returns only for approval.
- You can teach a task by showing a Bot a workflow once. It saves the workflow as a routine that takes your corrections. Recordings are capped at 10 minutes.
- The docs recommend testing a learned skill on a one-off task before turning it into a routine.

**Examples of use (from the launch post)**

- Internal use for sales outbound, marketing campaigns, office operations, and bug fixes.
- Suggested pilots: CRM updates from call transcripts, invoice processing, and bug triage.

**Limits**

- Each Bot can run one computer-use task on its screen at a time. Parallelism comes from adding Bots.
- Beta, with enterprise access on a waitlist and gradual team rollout.
- No usage quota is published. Weekly usage is included, with on-demand usage billed by model and token cost.
- The underlying model is not named.

**Pricing and access**

- No standalone price. Access comes with SuperGrok Heavy or Cursor's top tiers.
- Cursor Ultra is $200/month, and Cursor's own pricing data corroborates this.
- x.ai lists a "Premium Teams" seat at $120/month. Cursor's data lists plain Teams at $40/seat and no matching Premium SKU, so the $120 figure is unverified.

**Platforms**

- Documented: macOS (Apple silicon and Intel), Windows (x64 and Arm64), and iPhone on iOS 18 or later.
- Linux desktop, Android, and iPad are unsupported at launch per the docs. The download page appears to list a Linux build, which conflicts with the docs.

**Security caveats**

- xAI's docs state, on two pages, "Do not use separate Bots as a security boundary."
- Files, browser sessions, and CLI credentials are shared across all Bots on an account.
- Deleting a Bot is soft. It removes the profile, conversation, and routines, but files and logins may remain.
- Passwords, passkeys, 2FA, CAPTCHAs, and payments hand control to the human. A masked secret request exists for supported connections and is "not a general-purpose password manager."
- Data handling follows Cursor's account and privacy settings, including training opt-out and retention. Cloud storage is required, and Legacy Privacy Mode is not supported.

**How it differs from related products**

- **Grok Build:** xAI's terminal coding agent, a separate product with its own history.
- **Build Mode:** A prompt-to-app builder in the consumer Grok experience, not Grok Bot.
- **Grok 4.5:** A separate model released in July. The page does not link it to Grok Bot.
- **Grok chat and ChatGPT agent:** The page does not compare Grok Bot to either.

**Routines (schedules)**
- A routine tells one Bot when to run a workflow, on a schedule or, where supported, after an event.

- Require approval for sending, purchasing, deleting, publishing, or changing production systems.
- Example rules: "Do not contact customers." Customer contact always requires approval.
- Grok Bot may ask whether to keep routines running after a long absence. If there's no response, it pauses them.

**Testing**
- Use **Test run** after creating or editing a routine. It performs real work, so use safe inputs.
- Check that it selected current inputs, met the output format, left an audit trail, stopped at the approval point, and reported failures clearly.

**Managing routines**
- Open the Bot, choose **View conversation details**, then **Routines**.
- Available actions: enable or pause, run a test, edit schedule or instructions, review run history, and delete.

**Limits**
- Up to 50 routines per Bot.
- The app keeps the 20 most recent run records per routine.
- Schedules must be at least five minutes apart.
- Deletion is immediate with no undo. Deleting a Bot also deletes its routines.

## Approvals
- **Options:** Each approval request can be allowed once, denied, or turned into an always-allow rule. The article recommends "Allow once" while a workflow is new.
- **Always-allow:** Create one only after you can state the exact action, its scope, and what happens if it fails.
- **Auto Review:** The article mentions an "automatic review system" that can hold both Require Approval and Always Allow rules, but it doesn't explain how that review works. Its precedence rule is explicit: "A require-approval rule wins when both match."
- **Risky actions:** Sending, publishing, purchasing, deleting, permission changes, production changes, and accepting legal terms all need approval.
- **Scope:** Avoid broad rules like "always allow browser actions," because the browser reaches every signed-in service.

## Shared computer and security boundary
- Each user gets one persistent cloud computer, and all of their Bots share it, including files, browser cookies, signed-in sessions, and command-line credentials.
- The article states that "two Bots are not separate security boundaries." Duplicating a Bot doesn't isolate it.
- Each Bot has its own screen, so several can work in interfaces at once.
- Deleting a Bot removes its profile, conversation, and routines, but not its files or sessions on the shared computer.
- **Team Bots differ:** each teammate's chat runs on that teammate's own computer. A Slack channel or thread shares one separate computer for that Bot.

## Credential handoff
- For passwords, passkeys, 2FA codes, and CAPTCHAs, take over the computer and enter the value yourself.
- Connector API keys go in a secure credential field. Grok Bot stores them separately, makes them available only to that connector, and doesn't give the raw key to the Bot.
- Refuse any request to paste a `.env` file or key into chat.
- Never store connector secrets under `/workspace`, since every Bot can read it.
- **Team Bots:** teammates never see secret values, and the Bot uses them by name. But the Bot can use any secret in any teammate's conversation, so use scoped, read-only service-account keys.

## "One task per screen"
The article doesn't use this phrase. The closest guidance is that each Bot has its own screen, so several can operate interfaces in parallel while sharing the same files and sessions.

## Bots messaging each other and group chats
- A Bot can start work when you message it, when a routine or event triggers it, or when another Bot calls it.
- Group chats can have Bots decide whether to answer unaddressed messages. Behind the scenes, the host wakes each member in turn, which costs time and usage.
- For sequential work, message one owner Bot and have it call specialists.
- Handoffs should name the output path, what was completed, the evidence, what remains open, and the next owner. Put shared files under `/workspace` and keep secrets out of them.
- Up to 50 Bots and group chats combined are supported. Use a workforce-checker Bot to nudge stalled work.

## Connectors
- Plugins are the preferred route. Mention one with `@`. The article's preferred order is plugin, then API or CLI, then cloud browser, then local computer.

## The rule
- **Give it a job, not a prompt.** It works through the job across your logged-in apps and only comes back for approvals.
- **Skills are the how, routines are the when.** Turn a repeated task into a skill first, then give it a schedule or trigger and an approval boundary.
- **One account means one computer.** Every Bot can reach every file and login on it, so isolate access with scoped credentials, not extra Bots.
- **Approvals are the safety layer.** Approval rules beat always-allow rules, and wide always-allow rules are where things go wrong.
- **Each Bot does one thing on screen at a time.** For parallel work, add Bots and have one Bot hand work to the others *(unverified detail)*.
