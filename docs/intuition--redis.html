# Intuition: The Origin of Redis

## Elevator Pitch
In 2009 Salvatore Sanfilippo (antirez) was building LLOOGG, a real-time "who's on my site right now" analytics tool for tiny Italian web hosts. Every page view was a write, and the query was always the same: "show me the last N events for this site." MySQL choked on the write rate, and the pain was that the database made him translate a trivially simple idea — *a capped list per site* — into rows, indexes, and DELETE queries. So he wrote a server that just *was* a list. Then a set, a hash, a sorted set. That server is Redis.

**If you remember nothing else:** Redis exists because someone needed a list in memory that survived across processes, and no database at the time would let him say "list" without translating it into "table."

## In the Wild (STAR)
- **Situation:** A one-person startup ships a JavaScript snippet that pings a server on every page view across a few thousand sites. The product page shows the *latest 100 views per site*, live. Data older than that is worthless.
- **Task:** Each ping is an INSERT; every dashboard refresh is a `SELECT … ORDER BY ts DESC LIMIT 100`; and something has to DELETE the old rows or the table grows forever. On a single cheap VPS, MySQL's disk-bound writes fall behind by mid-afternoon. Adding a bigger box costs more than the product earns.
- **Action:** Replace the table with an in-memory server where the whole operation is two commands: `LPUSH site:42 <event>` then `LTRIM site:42 0 99`. The data structure *is* the schema; the cap *is* the retention policy. Snapshot to disk every few seconds.
- **Result:** Writes go from disk-bound to memory-bound — orders of magnitude more throughput on the same box. The bill: if the process dies between snapshots, you lose a few seconds of views, and the working set must fit in RAM.

**The tell:** (1) Your access pattern is a *named operation on a data structure* ("push and cap," "add to set," "increment counter"), not an ad-hoc query. (2) Losing the last few seconds of data is embarrassing, not catastrophic.

## The Key Insight
**Before:** a database is a store of records you query; durability is non-negotiable; data structures live in your process and die with it. **The flip:** treat the *data structure itself* as the unit the server understands, keep it in RAM as the primary copy (not a cache in front of something), and make durability a tunable dial rather than a premise. Once you accept "memory is the database, disk is the backup," lists, sets, and sorted sets with O(1)/O(log n) operations fall out naturally — and so does the "Remote Dictionary Server" name. Everything else about Redis (single-threaded event loop, atomic commands, pub/sub) follows from making that one bet.

## Negative Space
- **Not memcached.** Memcached's values are opaque bytes; you fetch, mutate in your app, and race to write back. In Redis the server mutates the structure, so `LPUSH` from ten clients is atomic without locks — and Redis can persist, which memcached never claimed.
- **Not a cache in front of a database.** A cache can vanish without consequence; in LLOOGG there *was* no other copy. Redis was born as a primary store with weakened durability, and "cache" was a use people found later.
- **Not a queue** (originally). Lists made queues easy, but there was no delivery guarantee, ack, or consumer group until Streams a decade later. It never claimed to solve exactly-once delivery — or ad-hoc querying across keys.

## Failure Space

**Working set outgrows RAM**
- **Trigger:** Data grows past memory; you don't notice because writes still succeed.
- **Mechanism:** Either eviction policies silently drop keys you thought were durable, or the box swaps and the single-threaded loop stalls on every command.
- **Breaks:** "The dataset is small enough to be an in-process structure" — true for last-100-views, false for "all events ever."

**Big-O on the wrong side**
- **Trigger:** Someone runs `KEYS *`, `SMEMBERS` on a million-member set, or `LRANGE 0 -1`.
- **Mechanism:** One thread serves everyone; one O(n) command blocks every other client for its full duration. Looks like network latency; it's head-of-line blocking.
- **Breaks:** "Every command is fast" — Redis only promised that for the *operations it was designed around*, not for every operation it exposes.

**Durability dial left at the default**
- **Trigger:** Redis becomes the system of record for orders, not page views; nobody revisits `save` / `appendfsync`.
- **Mechanism:** Crash between snapshots loses the last N seconds of writes; nothing errors, data is just gone.
- **Breaks:** "Losing a few seconds is fine" — the assumption LLOOGG's problem made *true*, silently carried into a problem where it isn't.

## Explain in Levels
**To a student:** Imagine keeping a notepad of the last 100 visitors on your desk instead of filing every visitor in a cabinet downstairs. Writing on the notepad is instant; every so often you photocopy it in case the desk catches fire. Redis is a notepad you can share across computers.

**To an engineer:** A single-threaded event loop over an in-memory dictionary whose values are real data structures (list, set, hash, sorted set); commands are atomic by construction because nothing runs concurrently. Persistence is RDB snapshots (fork + copy-on-write) and/or an append-only log with configurable fsync. Reach for it when your access pattern is a named structural operation and your working set fits in RAM; avoid it as a general query engine.

**To a PhD:** Redis is a linearizable single-node state machine over a key→ADT map, trading the durability leg of ACID for latency by decoupling the commit point from fsync. Persistence via fork exploits OS copy-on-write to get a consistent snapshot at near-zero pause cost, at the price of memory amplification under write-heavy loads. The design's subtlety is that atomicity is a *consequence* of serialization rather than a feature — which is exactly why the later additions (Lua scripting, MULTI/EXEC, Cluster's per-slot atomicity) had to be shaped around preserving that single-thread invariant.

## Rediscover It (Simulated Conversation)
**Marta:** MySQL's falling behind on the page-view inserts. Bigger box?
**Dario:** We're a two-person shop. What's the query, actually?
**Marta:** Always "last 100 events for site X." Nothing else. Ever.
**Dario:** Then index on (site, ts) and DELETE old rows on a cron.
**Marta:** Tried it. The DELETEs are the write load now. And every insert still hits disk.
**Dario:** Skip the DB — keep a per-site array in the web process, cap at 100.
**Marta:** Two things. We run four worker processes; each sees a quarter of the pings. And a restart wipes everything.
**Dario:** So it needs to be *one* process the workers talk to over a socket… which is basically a database again.
**Marta:** Only if it stores rows. What if it stores *the array*? The command is "append and trim," not INSERT.
**Dario:** And the restart problem?
**Marta:** Dump the arrays to disk every few seconds. If we lose five seconds of page views, nobody's dashboard notices.
**Dario:** So a server that holds lists in memory, speaks "push/trim" over a socket, and snapshots itself. That's… not a database. It's a shared data structure.

The two branches look unrelated — one is about I/O cost, the other about data modeling — but both bottom out on the same node: the server should hold the *structure*, in memory, as the real copy. Both consequences below it (single thread, snapshotting) are only reasonable *because* of that node.

## Feynman Gap-Check
Plain version: "Antirez needed a capped list shared between processes; databases made that slow and awkward; so he wrote a server that holds lists in memory and dumps them to disk periodically; it turned out lots of problems are shaped like that."
