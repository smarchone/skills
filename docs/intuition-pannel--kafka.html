❯ they're reading from different partitions
**CEO** — Correct. The guarantee was always *per partition*. "Topic ordering" doesn't exist. Layer 1 peeled.

**PM** — So the real question becomes: *who decides which partition a message lands in?* Answer: the producer, via the message **key**. Same key → same partition → ordered. No key → round-robin → chaos.

**Architect** —
```
key = order_id
  order 42: create ──► p0
  order 42: pay    ──► p0   ✓ ordered
  order 43: create ──► p1   (different order, don't care)

no key:
  order 42: create ──► p0
  order 42: pay    ──► p1   ✗ pay may be seen first
```

Fix: key by the thing whose order matters. Cost: **hot partitions** if one key dominates.

Next situation: you key by `customer_id`. One whale customer makes 60% of traffic. What breaks, and what do you do about it?

❯ one partition gets overloaded, add a salt to the key
**CEO** — Right diagnosis, and you just walked into the trade-off on purpose: salt the key and you **gave back ordering** for that customer. Kafka never lets you have both cheaply.

**PM** — The honest fix is picking a *finer* key whose order you actually need. Does whale's order 1 need to precede order 2? Usually not — key by `order_id` instead. Salt only when there's truly no natural finer grain.

**Architect** —
```
customer_id ──► p3 (60%)          ← hot
order_id    ──► spread across all  ← ordered per order, balanced
customer|salt ► spread, but events for one order may split ✗
```

Rule of thumb: key = the smallest unit whose internal order matters.

❯ make the fraud call async and use idempotency keys
**CEO** — Idempotency keys: yes, non-negotiable, that's the real fix for (b). "Make it async": careful — you just created a new problem. Which one?

**PM** — If you fire the fraud call async and keep polling, you'll commit offsets for records whose fraud check hasn't finished. Consumer dies → those records are marked done → payments skipped fraud entirely. You traded at-least-once for **at-most-once** on the most important step.

**Architect** — The actual pattern:
```
poll ─► decouple ─► pause(partition) ─► work queue ─► fraud API
                                          │
        commit only up to the lowest      ▼
        fully-processed offset  ◄──── ack tracker
        resume(partition) when queue drains
```
`pause()`/`resume()` keeps the heartbeat alive without fetching more. Commit tracks *completion*, not *receipt*. And `max.poll.records` down, so a batch is bounded by worst-case latency.

Next: idempotency keys are stored in Postgres. Fraud check passes, you write the key, you commit the offset — then Postgres write succeeds but the commit fails. Or vice versa. Which order do you do those two writes in, and why does it still not fully save you?

❯ before moving on to more scenarios, can you list non trivial abstractions and guarantees for operating with kafka ?
**Architect** — The ones people get wrong. Each is a "trust this, until…" line.

**Ordering**
- Order is per partition, never per topic.
- Producer `retries` + `max.in.flight > 1` can reorder within a partition — unless `enable.idempotence=true`.

**Durability**
- `acks=all` means "written to all *in-sync* replicas" — and the ISR can shrink to 1. `min.insync.replicas` is what actually sets the floor.
- Committed offset ≠ processed. It's your claim, nothing else.
- A message is only visible to consumers once it's replicated to the ISR (high watermark). Leader-ack'd ≠ readable.

**Delivery**
- Default is at-least-once. Exactly-once exists only inside Kafka→Kafka (transactions). Once you touch an external system, you're back to idempotency.
- Consumer transactions: `read_committed` isolation, else you see aborted records.

**Consumers**
- One partition → one consumer in a group. More consumers than partitions = idle consumers.
- Heartbeat and poll are different liveness signals. Alive-but-not-polling still gets kicked.
- Rebalance = stop-the-world for the group (unless cooperative-sticky).
- Offsets are stored per group in `__consumer_offsets` and **expire** — a dormant group comes back with `auto.offset.reset`, which might be `latest` = silent data skip.

**Retention**
- Retention is by time/size, not "until consumed." Slow consumers lose data silently.
- Compacted topics keep *latest per key* — but only eventually, and tombstones vanish after `delete.retention.ms`.

**Producers**
- `send()` is async and buffered. Returning ≠ sent. Process exit without `flush()` = lost.
- Idempotent producer dedups only within one session + one partition.

**Cluster**
- Partition count can only go up, and going up **breaks key→partition mapping** for existing keys.
- Unclean leader election: `false` = availability loss, `true` = data loss. Pick one.

❯ so atleast once is the default delivery guarantee... and for exactly once processing guarantee, we need idempotent keys and state maintainance at consumer side
**CEO** — Yes, with one sharpening: "exactly-once" isn't something Kafka gives you. It's something you *build* out of at-least-once + dedup. Kafka's job is to never lose; yours is to never double-apply.

**PM** — And the state has to live *where the effect happens*, atomically with it. Idempotency table in Postgres + payment row in Postgres, same transaction = real. Idempotency in Redis + payment in Postgres = two writes, one can fail, back to square one.

**Architect** —
```
     at-least-once (Kafka)
   + idempotent effect (your store, same txn)
   = effectively-once
```
The offset commit is then *just an optimization* — replay is harmless, so its ordering relative to the DB write stops mattering. That's the answer to my earlier question: make the offset commit irrelevant instead of ordering it carefully.

Corner you should still feel: dedup table grows forever. When do you evict a key, and what's the risk if a replay arrives after eviction?

❯ should we deploy consumers via rolling restart ?
**CEO** — Rolling isn't the problem. *Eager* rebalancing is. With the default assignor, every instance restart = whole group stops, all partitions revoked, reassigned. 8 instances rolling = 16 stop-the-world events.

**PM** — Two knobs change the story:
- `partition.assignment.strategy = CooperativeStickyAssignor` — only the leaving instance's partitions move, the rest keep working.
- `group.instance.id` (static membership) + `session.timeout.ms` ≥ restart time — the broker treats the restart as a blip, no rebalance at all.

**Architect** —
```
eager:        [stop all] ─ reassign ─ [start all]   × per instance
cooperative:  p3,p4 move ────────────  others untouched
static:       "brb" ─ same instance returns ─ nothing moves
```
Cost of static: if an instance *actually* dies, nobody picks up its partitions until session timeout expires. You traded restart smoothness for slower failover.

So: rolling yes, but with cooperative + static, and `session.timeout` tuned to your real deploy time — not the default 45s if your pod takes 90s to come up. What's your pod startup time?
✻ Done in 9s
❯ why even have egar assignment
**CEO** — History, mostly. Eager is the original protocol (2012). Cooperative landed in 2.4 (2019). It's default only because changing defaults breaks upgrades.

**PM** — But there's one real reason it exists: **simplicity of correctness**. Eager = "everyone drops everything, nobody owns anything, then reassign." There's never a moment two consumers think they own the same partition. Cooperative needs two rounds and careful revocation to guarantee that.

**Architect** —
```
eager:        1 round.  revoke-all → assign.   trivially safe.
cooperative:  2 rounds. assign-minus-moving → revoke → assign-moving.
              a client with a buggy rebalance listener can double-own for a beat.
```
Also: you can't mix. Rolling from eager → cooperative needs a two-step upgrade (add cooperative alongside eager, then remove eager), or the group refuses to form.

So: use cooperative. Eager is the training wheels that shipped first. Next scenario, or dig into the double-own edge?
✻ Done in 7s
❯ any issue with a cooperative assignment when there is no rolling restart ?
**CEO** — Yes, one subtle one: cooperative is *sticky*. It optimizes for not moving partitions. That's great until the current assignment is bad.

**PM** — Scenario: 3 consumers die one at a time, partitions pile onto the survivors. Then 3 fresh ones join. Cooperative moves the *minimum* to reach balance — but "balance" is by partition count, not by load. Your hot partition stays wherever it landed.

**Architect** —
```
after churn:   c1: p0 p1 p2 p3(hot)    c2: p4 p5    c3: p6 p7
cooperative:   moves p2 to c2 → count-balanced, load not.
```
Second: if your rebalance listener does work on revoke (flush, commit), cooperative fires it more often in small doses vs eager's one big hit — code assuming "revoke = I own nothing now" is wrong; you may still own others.

Third: scaling out mid-lag. Cooperative rebalances while the survivors keep consuming — good — but new members won't get anything until the *next* round, so a lag spike drains slower than you'd expect for a few seconds.

None fatal. Just: sticky ≠ balanced, and revoke ≠ empty.
