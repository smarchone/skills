# Claude Code Projects: one agent you talk to, many agents doing the work
**Source:** launch coverage of Claude Code Projects (beta, 17 Sep 2026): [dsebastien.net](https://www.dsebastien.net/claude-code-projects-stop-managing-sessions-talk-to-one-agent/), [eesel.ai](https://www.eesel.ai/blog/claude-code-projects) · **For:** PM
> Source note: secondhand only. The official docs page returned 404 and the X announcement wasn't opened. eesel is a competing vendor. No Projects-specific pricing or limits were published.

## CEO note
**What's happening:** Claude Code moves from "you run sessions" to "you state a goal." One long-lived agent splits the goal into threads, runs them as parallel cloud sessions, and keeps the memory.
**Why it matters:** the developer stops being the orchestrator. Mollick's run had 18 threads, each starting its own sub-agents, for about a day of work — "an organization to solve your problem."
**The real constraint:** cost and auditability, not capability. Every thread is a full session that draws on the same subscription limits.
- **Opportunity:** a single entry point for vague, multi-day goals that no other surface handles.
- **Threat:** it burns through limits and turns out work nobody can review. Users will blame the plan, not the feature.
- **Watch:** per-project spend, how legible each thread is, and the rollout to Team and Enterprise.

**Bottom line:** the product isn't parallelism, it's *delegation you can trust without watching*.

## The product
| Capability | What it does | Status |
|---|---|---|
| Orchestrator agent | One persistent conversation per project. It holds the memory, plans and delegates | Beta |
| Threads | The goal is split into parallel cloud sessions that keep running after the laptop closes | Beta |
| Context passing | The orchestrator moves context between threads and assembles the result | Beta |
| Memory | Remembers how the user works across the project | Beta |
| Proactive / scheduled runs | The project can act on its own or on a schedule | Beta |
| Model mixing | Uses expensive and cheap models according to user preference | Beta |
| Surfaces | Desktop app and web (claude.ai/code) | Select Pro and Max users; "everyone soon"; Team and Enterprise not yet ⚑ (sources conflict) |

**How it fits:**
```
 you ── goal, stray thoughts ──▶ PROJECT (orchestrator: plan · memory · review)
                                     │ splits / passes context
                     ┌───────────────┼───────────────┐
                  thread 1        thread 2  ...   thread N    (cloud sessions,
                  └─ subagents    └─ subagents    └─ subagents  same setup layer:
                     └───────────────┼───────────────┘          CLAUDE.md, skills,
                                     ▼                          MCP, hooks)
                          assembled result ──▶ you review
```
**Loop:** state goal → orchestrator scopes and splits → threads run in parallel → orchestrator reviews and assembles → you steer → memory gets updated → next goal.

**Where it sits among Claude Code's multi-agent features:** Agent View (you dispatch, you orchestrate) · Agent Teams (local, experimental) · Routines (one saved task plus a trigger) · `ultracode` workflows (deterministic, scripted fan-out) · **Projects (persistent, plans and remembers)**. Workflows are for control and repeatability; Projects are for messy goals you come back to.

## PM view
**Experience vision**
- **Work starts as a conversation, not a session.** You talk to one agent, and Boris Cherny's habit is to send thoughts as they come and let Claude sort them into threads.
- **Your role moves from dispatcher to client.** You scope and review; you don't babysit five terminals.
- **Work outlives your attention.** Threads run in the cloud, can run on a schedule, and pick up where they stopped.

**Impact claimed:** about a day of work coordinated from one prompt (Mollick, 18 threads). There's no official productivity number.

**Novel approaches**
1. **Delegation is the default interaction.** The user never chooses how many agents to run.
2. **Memory is scoped to the project, not to a session or a repo.** It's the thing that makes "come back to it later" work.
3. **Built-in skeptic agents.** Mollick's run ended with agents fact-checking the other agents' write-ups. Review is part of the plan, not something done afterward ⚑ (it isn't clear whether this is a default or something the prompt asked for).
4. **Model mixing as a preference.** Cost control is set as a policy, not by picking a model per call.

**Gaps and open questions**
- **Spend is invisible upfront.** No estimate or cap per project, and threads fan out on their own. This is the biggest risk to trust.
- **Auditability.** With 18 threads × sub-agents, what did each one do, and why? There's no evidence of a per-thread trace or summary in the sources.
- **Naming collision** with Claude app Projects, which are knowledge bases for chats. Expect support confusion.
- **Setup still decides quality.** Threads inherit CLAUDE.md, skills and MCP, and users report 2–3 weeks to dial that in.
- **Team use is unclear.** No word on shared projects, permissions, or plans other than Pro and Max.

## Architect view
| Layer | Component | Key property |
|---|---|---|
| Surface | Desktop and web conversation | One agent is the entry point |
| Orchestration | Long-lived orchestrator, said to share an architecture with Claude Tag | Holds plan and memory; delegates |
| Execution | Cloud Claude Code sessions per thread, plus their own subagents | Parallel, survives disconnects |
| Context | Project memory plus the per-repo setup layer | Context is passed between threads by the orchestrator |
| Governance | Shared usage pool (5-hour window plus weekly limits) | No per-project budget surfaced |

| Decision | Chosen | Gives up |
|---|---|---|
| Planning | **Model-planned fan-out** | Determinism and repeatability (that's what `ultracode` workflows are for) |
| Execution | **Cloud sessions** | Local tools and machines; cost moves to the user's limits |
| Memory | **One orchestrator holds the state** | Threads see only what the orchestrator passes on ⚑ |
| Billing | **Same pool as chat and terminal** | Isolation: one runaway project can starve everything else |

**Hard problems**
- **Context handoff.** What the orchestrator passes to each thread decides quality, and a lossy summary means duplicated or conflicting work ⚑.
- ⚑ **Conflicting edits.** Parallel threads touching the same repo need branch or merge discipline.
- ⚑ **Runaway fan-out.** Recursive sub-agents need depth and budget limits at the orchestrator.
- **Trace and replay.** Auditing many threads needs a structured record of each thread, not raw transcripts.

**Extension points:** threads use the existing setup layer (CLAUDE.md, skills, MCP, hooks), so any investment in a repo's setup pays off in every thread.
